# UNO Q の Linux 側で動かす前提のモデル設計

作品「口笛を真似るちくわ笛ロボット」の AI 部分を、Arduino UNO Q の Linux 側(Qualcomm QRB2210)で推論・学習まで完結させるための設計メモです。

## 前提

| 項目 | 内容 |
|---|---|
| CPU | Arm Cortex-A53 × 4(最大 2.0GHz) |
| RAM | 2GB または 4GB |
| OS | Debian 系 Linux |
| 実行環境 | Python 3 + numpy のみ(PyTorch などの深層学習フレームワークに依存しない) |
| アクセラレーター | 使わない前提(GPU・DSP の利用は将来の選択肢) |
| MCU との接続 | Arduino Bridge(RPC)。演奏プロファイルの送信と、演奏ログの受信 |

numpy だけに絞る理由:

- UNO Q の App Lab の Python 実行環境に、どこまで追加パッケージを入れられるかが未確認
- この作品のモデルは数千〜数万パラメータで、深層学習フレームワークの恩恵が小さい
- 学習に進化戦略(ES)を使うので、自動微分が要らない

## 処理の流れと置き場所

```
[口笛を録音 48kHz] → [YIN で音程軌跡] → [お手本(10ms 刻み)]
        │                                     │
        │                     [方策でプロファイル生成(1 テイク分を一括)]
        │                                     │  Bridge で送信(10 秒で約 4KB)
        │                                     ▼
        │                        MCU: プロファイルを 100Hz で正確に再生
        │                             + マイク録音(演奏ログ)
        │                                     │  Bridge で受信
        ▼                                     ▼
                  [YIN で演奏の音程軌跡] → [お手本と比較(報酬・ずれ)]
                                              │
                        [次のテイクの観測に「前回のずれ」を入れて再生成]
                        [ログを貯めて、世界モデル・方策を追加学習]
```

**演奏中に Linux 側がリアルタイムで判断する処理はありません。** Linux 側の処理はすべて「テイクとテイクの間」に行うので、Linux の非リアルタイム性や Bridge の遅延が演奏の質に影響しません。リアルタイムの補正(フィードバック)は、小型化した補正方策を MCU に載せて行います(後述)。

## モデル一覧

| # | モデル | 構造 | 規模 | 実行場所・タイミング |
|---|---|---|---|---|
| 1 | 音程抽出 | YIN(学習なし)。笛の音域は 16kHz、口笛は 48kHz | パラメーターなし | Linux、録音の後 |
| 2 | 基準コントローラー(物理モデル) | 公称の管の式 + 推測航法 + 発音補償の角度 | 数値 20 個程度 | Linux、プロファイル生成時 |
| 3 | 反復学習制御(ILC) | テイクごとに音程の補正量を更新 | テイク長 × 1 | Linux、プロファイル生成時 |
| 4 | 残差方策(基本方策) | MLP: 観測 229 次元 → 隠れ層 32(tanh)→ 2 | 約 7,400 パラメーター(float32 で約 30KB) | Linux、プロファイル生成時 |
| 5 | 世界モデル | 物理パラメーター(`FluteParams`)の当てはめ + 残差の小型 MLP | 数十〜数千パラメーター | Linux、テイクの記録から更新 |
| 6 | 補正方策(フィードバック) | MLP: 遅れた音程のずれ等 約 30 次元 → 16 → 2 | 1,000 パラメーター未満 | Linux で学習し、MCU で推論 |

### 基本方策は「プロファイルを一括で生成」する

演奏中は音を聴かないので、方策は 1 テイク分(例: 10 秒 = 1,000 ステップ)のプロファイルを**演奏前にまとめて生成**できます。方策は自分の過去の行動を観測に使うので逐次計算になりますが、1 ステップの推論は数十 µs 程度なので、10 秒分でも数十 ms で終わります(下の計測値を参照)。

生成したプロファイル(PWM と角度 × 1,000 ステップ、int16 なら約 4KB)を Bridge で MCU に送り、MCU がタイマーで 100Hz 再生します。

### 学習の分担

| 段階 | 場所 | 内容 |
|---|---|---|
| 事前学習 | PC(または UNO Q で時間をかけて) | ドメインランダム化したシミュレーターで ES。数十〜数百世代 |
| 世界モデルの実測合わせ | UNO Q | 実機のテイクの記録から `FluteParams` を当てはめ直す(数十〜数百テイク分のログ) |
| 方策の追加学習 | UNO Q | 当てはめた世界モデルの中で ES を数世代。練習の合間に実行 |
| テイク間の上達 | UNO Q | ILC または学習した方策が「前回のずれ」を使って次のプロファイルを出す(学習の計算は不要) |

## 計測値

計測値は `scripts/bench.py` で取ります。UNO Q の実機では、この表を実測値に置き換えます。

| 処理 | PC 実測(Core i7 第 8 世代、1 コア) | UNO Q の見込み(×5〜10 と仮定) |
|---|---|---|
| シミュレーター 1 ステップ | 105 µs | 0.5〜1 ms |
| 物理モデルの基準コントローラー 1 ステップ | 22 µs | 0.1〜0.2 ms |
| 残差方策 1 ステップ(隠れ層 32 / 7,426 パラメーター) | 42 µs | 0.2〜0.4 ms |
| 残差方策 1 ステップ(隠れ層 128 / 29,698 パラメーター) | 48 µs | 0.25〜0.5 ms |
| **1 テイク(10 秒 = 1,000 ステップ)のプロファイル生成** | **約 42 ms** | **約 0.2〜0.4 秒** |
| YIN 1 フレーム(1,024 サンプル @16kHz) | 133 µs | 0.7〜1.3 ms |
| 10 秒の録音の音程抽出(1,000 フレーム) | 約 0.13 秒 | 約 0.7〜1.3 秒 |
| ES 1 世代(16 候補 × 4 エピソード × 3 テイク) | 約 10 秒 | 約 1〜2 分(4 コア並列なら 1/4 程度) |

UNO Q の列は、Cortex-A53 の numpy が PC の 1 コアより 5〜10 倍遅いと仮定した**見込み**です。実機で `bench.py` を実行して置き換えます。

この見込みでも、**テイクの合間の処理(録音の解析 + 次のプロファイル生成)は合計 1〜2 秒程度**に収まり、練習の流れを止めません。ES による方策の学習は 1 世代 1〜2 分かかるので、実機では「練習の合間に数世代」、事前学習は PC で行う分担にします。

隠れ層を 32 から 128 に増やしても推論時間はほとんど変わりません(Python の呼び出しの手間が支配的なため)。モデルの大きさは、推論時間ではなく学習の安定性で決めてよいことになります。

## メモリ

- モデルのパラメーター: 合計 100KB 未満
- 1 テイクの記録(10 秒、数チャンネル × 1,000 ステップ): 数十 KB
- 録音(48kHz・16bit・10 秒): 約 1MB
- 合計しても数十 MB に収まり、2GB モデルでも問題にならない

## 実機で確認すること

- [ ] App Lab の Python 環境で numpy が使えるか(使えない場合の代替: 別の Python 環境を Linux 上に用意する)
- [ ] `scripts/bench.py` の実測値(A53 での所要時間)
- [ ] Bridge でプロファイル(約 4KB)と演奏ログを、テイクの合間に許容できる時間でやり取りできるか
- [ ] 48kHz の録音が、Media Carrier のマイク端子(または USB マイク)から取れるか

## 将来の拡張

- 観測をもっと長い時間で扱いたくなったら、MLP を GRU などの系列モデルに置き換える。その場合は ONNX Runtime(aarch64 版がある)での推論を検討する
- 補正方策を MCU に載せるときは、重みを int8 に量子化して C の配列として書き出す
