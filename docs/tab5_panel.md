# Tab5 のタッチパネル（I2C の有線）— 2026-11-25

M5Stack Tab5 を、やまびこ1号の演奏用の簡易 UI にする。UNO Q とは **B 基板の予備 I2C（J3）** で有線につなぐ。
Wi-Fi や会場のネットワークに頼らない。

## 1. 配線

Tab5 の PORT.A（Grove、HY2.0-4P）と B 基板の J3（XH 4 極）をつなぐ。

| Tab5 PORT.A | 線の色 | B 基板 J3 | 
|---|---|---|
| GND | 黒 | 2 GND |
| G53（SDA） | 黄 | 3 SDA |
| G54（SCL） | 白 | 4 SCL |
| 5 V | 赤 | **つながない**（J3-1 は 3.3 V） |

- SDA / SCL は B 基板で 3.3 V へ 4.7 kΩ で引き上げてある（R9・R10）。Tab5 は自分の電源（USB-C か電池）で動かす
- J3 は MCU の I2C4（PF14 / PF15、J15-16 / 18）。UNO Q の Arduino コアの既定の I2C4 は PD12 / PD13 なので、ファームウェアがピンを PF14 / PF15 に付け替える
- 速さは 100 kHz。ケーブルは短め（50 cm 程度まで）を想定

## 2. 仕組み

```
Tab5（I2C の親） ──I2C──> UNO Q の MCU（子、0x42） ──シリアル──> 演奏サーバー ──TCP──> 演奏ページのプロセス
                 <── ページ（状態・グラフ）                 <── cmd panel             <── PanelBridge
```

- **ボタン**（録音・練習：もう一度・止める）: MCU の EXEC ボタンを押したのと同じ扱い（押した回数に足す）。
  演奏サーバーは演奏中ほかの命令を受けないが、ボタンは見ているので、**演奏中・キャリブレーション中でも止められる**
- **そのほかの要求**（版の選択・キャリブレーション・お手本の演奏）: MCU が Linux へ 'U' の小包で送り、演奏ページのプロセス（`PanelBridge`）が実行する
- **画面のページ**: 演奏ページのプロセスが、状態が変わるたびに 1 ページ（約 0.5〜2 KB）を作って送る（`flute_rl/yamabiko/panel.py`）。
  MCU は 2 枚のページを持ち、送り終えた方に切り替えるので、半分だけ新しいページは見えない。5 秒ごとに送り直す（MCU が書き直しや再起動でページを失っても戻る）
- 演奏中は、送る経路（演奏サーバー）がふさがるので、演奏が始まる直前のページ（「演奏中」と曲の長さ）を Tab5 が自分の時計で進めて見せる

### I2C のやりとり（MCU は 0x42）

| 書く | 中身 |
|---|---|
| `0x01 n` | EXEC ボタンを n 回（1: 録音・録音終了・止める、2: もう一度）。2 回は 150 ms 間隔 |
| `0x02 …` | Linux への要求（`0x10 i` 版を選ぶ、`0x11` キャリブレーション、`0x12 i` お手本を吹く） |
| `0x03 lo hi` | 次に読む位置 |

読むと `'Y' '1' 版(u16) 長さ(u16)` の後にページが続く。ページの中身は `panel.py` の説明と `tab5/yamabiko_panel/page.h`（2 つは同じに保つ）。

### ファームウェアの作り

UNO Q の Arduino コア（Zephyr）は I2C の子（ターゲット）機能が無効（`CONFIG_I2C_TARGET` なし）なので、`Wire.begin(addr)` は使えない。
`yamabiko_fw.ino` の `panel_poll()` が、メインループから I2C4 のレジスターを直接見て応答する。
アドレスが合ったら転送 1 回分をまとめて処理し、その間は SCL を引き延ばして親を待たせる（1 回 64 バイトで約 6 ms、100 kHz）。
音声は DMA のリング（約 43 ms）に溜まるので、その間に取りこぼさない。

## 3. 画面（1280×720 の横向き）

押している間はボタンが暗く沈み、離すと縁取りが光って短い音が鳴る（一覧の行・タブも押している間は色が変わる）。

### シリアルの API（USB、115200）

1 行 1 コマンド、答えは 1 行の JSON。PC からは `python scripts/tab5_cli.py <コマンド>`。

| コマンド | 働き |
|---|---|
| `status` | ページの版・状態・版とお手本の数・I2C の成功と失敗・送った押下と要求の数・画面の大きさ・PSRAM・起動からの時間 |
| `page` | 受け取ったページ（版の一覧、お手本の一覧、練習の成績、メッセージ、点の数） |
| `dump <位置> <数>` | 受け取ったページの生のバイト（16 進、128 まで） |
| `press 1` / `press 2` | EXEC ボタンを 1 回 / 2 回（笛が鳴ることがある） |
| `step <番号>` / `archive <番号>` / `calibrate` | 版を選ぶ / お手本を吹く / キャリブレーション（笛が鳴る） |
| `tap <x> <y>` | 画面のその位置をタップしたのと同じ |
| `tab steps` / `tab archive`、`bright <0-255>`、`log on` / `log off`、`redraw`、`help` | 一覧の切り替え、明るさ、タップ・押下・要求のログ、描き直し、一覧 |

`python scripts/tab5_cli.py watch 60` で、60 秒間のログ（タップ・押下・要求）を見られる。ポートを開くと Tab5 が再起動することがあり、`tab5_cli.py` は 2 秒ごとに送り直して待つ。

| 場所 | 中身 |
|---|---|
| 上 | 状態の色の点、状態（待機中・録音中・演奏中…）と使う版、メッセージ、その日の縮み切りの音 |
| 左 | 大きなボタン: 録音（録音中は「録音終了して演奏」）、練習：もう一度、キャリブレーション、止める。録音・演奏中は進み具合のバー |
| 中央 | 楽譜（黒）と最後の回に鳴った音（橙）のグラフ、練習の回ごとの誤差の棒グラフ |
| 右 | 「使う版」と「お手本」（アーカイブの声）を切り替える一覧。押すと版を選ぶ／そのお手本を吹く |

ボタンが押せるかどうかは演奏ページと同じ決まり（例: 練習は曲があって止まっているときだけ、止めるは動いているときだけ）。
UNO Q からの応答が 3 秒途切れると「UNO Q と通信できません」と出す。

## 4. 書き込みと起動

**Tab5**（PC の Arduino IDE か arduino-cli。ボード「M5Tab5」、**ライブラリ M5Unified 0.3.0・M5GFX 0.3.0 以上**）:

> M5GFX 0.2.9 までは Tab5 の液晶として ILI9881C しか知らず、新しい製造分の Tab5（液晶 ST7123）では、起動もタッチも I2C も動くのに**画面が真っ黒**になる（2026-11-25 に実機で起きた）。0.3.0 で ST7123 に対応している。起動時に USB のシリアル（115200）へ、ボードの種類・画面の大きさ・キャンバスを確保できたか・PSRAM を出す。


```
arduino-cli compile --upload -p <Tab5 の COM ポート> tab5/yamabiko_panel
```

`tab5/yamabiko_panel/sketch.yaml` が、16 MB フラッシュと 3 MB のアプリ区画（`FlashSize=16M,PartitionScheme=app3M_fat9M_16MB`）を選ぶ。
日本語フォントで約 2 MB になり、既定の区画（1.2 MB）には入らない。Arduino IDE ならツールメニューで同じものを選ぶ。

**UNO Q**: ファームウェア（`yamabiko_fw.ino`）を書き込み、演奏ページを起動し直す（`PanelBridge` は既定で動く。止めるなら `--no-panel`）。

## 5. 実機でつないだとき（2026-11-25）

Tab5 に書き込んで J3 につなぎ、次の 3 つを直した。

| 起きたこと | 原因 | 直し方 |
|---|---|---|
| 1 秒に 1 回ほど失敗し、そのたびに MCU のループが最大 30 ms 止まり、シリアルの命令を大量に取りこぼした（cmd_bad が 12 分で 14 万） | 転送 1 回分をまとめて待つ作りで、Tab5 が途中で諦めると 25 ms 待ち続けた | ループの 1 周ごとに 1 歩ずつ進める作りにした（バイトの間は SCL の引き延ばしで Tab5 を待たせる） |
| 十数秒で I2C が止まり、SCL が Low に張り付いた | 前の転送の STOP と次の転送の開始（ADDR）が同時に届くと、開始を先に処理してから STOP で「終わった」として捨てていた | STOP を先に処理する。誰の転送でもないまま 20 ms 使用中なら I2C を初期化し直す |
| ページを送るたびに命令を取りこぼした（20 秒で 58） | 37 バイトの小包を続けて送り、MCU の受信バッファがあふれた | Linux 側で小包の間を 2 ms 空ける（`hw.Link.panel`、1 ページ 40 ms ほど） |

| **触っていないのに押下・版の切り替えが起き、演奏が繰り返された** | 「次に読む位置」`0x03 下位 上位` の最後のバイトを受け取る前に STOP を処理し、残った「上位」が次の書き込みの先頭として読まれた。位置 262〜 で上位 `0x01`＝押下、518〜 で `0x02`＝要求になった（ページが 262 バイトを越えると起きる）。Tab5 は押下 0 回・要求 1 回なのに MCU は押下 27 回・要求 14 回と数えていた | 受信したバイトを STOP より先に取り込む。転送の外で残ったバイトは捨てる。直した後、2 分間で偽の押下・要求 0 |
| 止めるを押してもすぐ止まらず、止まった後にまた演奏が始まった | サーバーが演奏の本体でしかボタンを見ておらず、ファンの準備（2〜3 秒）と原点戻し（1.3 秒）の間の押下を見落とした。何度か押した余りが、止まった後に「2 回押し＝もう一度」になった | サーバーは演奏・キャリブレーションの最初にボタンの基準を取り、準備中も見る。画面のプロセスは止めた直後 1.5 秒の押下を無視する。Tab5 は止めるの後 2 秒、録音・練習・止めるを受け付けず「止めています」と出す |
| 右の一覧に step8 が出ない | 13 個の版が一覧の高さ（12 行分）に入らず、最後が切れた | 行の高さを版の数に合わせて詰める |

直した後: やりとりは 1 秒に約 22 回、失敗は 0.6 %（自動で立ち直る）、命令の取りこぼし 0（30 秒）、SCL・SDA とも High に戻る。
Tab5 のキャリブレーションのボタンから、UNO Q でキャリブレーションが走ったことをサーバーのログで確かめた。
MCU の `info` の `PANEL` 行に、SCL・SDA の線の状態と I2C の状態（ISR）を足した（バスが止まったときの手掛かり）。

## 5. 確かめたこと・まだのこと

確かめた（2026-11-25）:
- ファームウェアを UNO Q に書き込み、音声の流れ（途切れ 0）・状態の送信・ボタンの数え方が変わらないこと
- I2C4 が PF14 / PF15、アドレス 0x42 で待ち受けていること（`info` の `PANEL` 行）
- 演奏ページのプロセスが作ったページが MCU に載ること（`page v3 584 bytes`）
- PC の偽の機体で、ページの送信と、パネルからの版の切り替えが動くこと（`tests/test_yamabiko_panel.py` ほか）
- Tab5 のスケッチがコンパイルできること

まだ:

- 書き込む前のファームウェアは UNO Q の `build_fw_before_panel/` に残してある
