# やまびこ1号 — 設計メモ

> **2026-09-21:** 本文の音程列＋物理制御方式は比較対象として残す。新しい本命は、生のお手本音声と生の自己音声から
> 1モデルでPWM・バルブ・終了を直接出す [E2E構成](e2e.md) とする。

2026-09-17 に決めた、作品のテーマを「笛を吹く強化学習」から
**「音を位置センサーに使う、エンコーダーレス直動制御」** にずらす案です。
全体の段階は [roadmap.md](roadmap.md) のまま、段階 1 の中身を差し替えます。

## 一行の主張

> 直動アクチュエーターに位置センサーを一切つけず、**笛が鳴っている音の高さだけ**を
> 位置のフィードバックに使って位置制御する。音程解析の遅れは、学習した観測器が
> フィードフォワードで補う。口笛を聞き終わってから、それをコピー演奏して見せる。

「やまびこ」は、聞いた音を返す動作と、この作品の売り(**聞いてから返す**)の両方を指します。

## なぜ AI が要るのか

前のテーマ(2 自由度の笛を強化学習で吹く)は、AI の必要性が薄いという弱点がありました。
実験でも、強化学習の寄与は古典制御とシステム同定の後に残った 10 セント程度でした
(README の結果 2〜5)。

テーマをずらすと、AI の役割が**制御器から観測器に移り**、必然性が立ちます。
音を位置センサーとして見たとき、その性質が悪いからです。

| 性質 | エンコーダー | 音響位置センサー(この作品) |
|---|---|---|
| 遅れ | ほぼ 0 | 10〜50ms、しかも個体ごとに違う |
| 欠測 | なし | 鳴っていない間は完全に無信号 |
| 曖昧性 | なし | オクターブ誤り = 位置が約 2 倍ずれる |
| 交差感度 | なし | 気温(約 3 セント/℃)、送風圧 |
| 線形性 | 線形 | `f = c / 4L` の非線形、分解能が位置で変わる |

この 4 つを同時に扱う観測器は手で書きにくく、学習でやる理由が自然に立ちます。
自由度の数は関係ありません。

数字の上でも、手柄の配分が変わります。README 結果 3 を観測器の話として読み直すと:

| 1 テイク目の音程のずれ | |
|---|---|
| 音を聞かない(推測のみ) | 165 セント |
| 音で位置を直す(手作りの観測器) | 62 セント |
| 音で位置を直す(学習した観測器) | **38 セント** |

リポジトリの中で強化学習が最も稼いでいるのは、まさにこの観測器の仕事です。

## ハード構成

| 部位 | 変更 | 理由 |
|---|---|---|
| 吹き口 | エッジに吹き付ける方式 → **リコーダー型(フィップル)** | 音が安定して出る。**音程が管長のほぼ純粋な関数になり、位置センサーとして素直になる** |
| 笛全体 | **スライドホイッスル型**(フィップル + 底をプランジャーで塞いだ閉管) | 同じ機構の楽器が既製品としてある。買って改造する道と、頭部管だけ 3D プリントして筒をちくわにする道の両方が取れる |
| 吹き込み角度サーボ(SCS0009) | **吹き込み角度には使わない**。発音の入切の回転円板弁に転用 | フィップルでは角度の調整が不要 |
| 送風 | **ファン**。再生開始前にオン、終了後にオフ。演奏中は回しっぱなし | 制御変数にしない |
| 発音の入切 | ~~3 方ソレノイドバルブで流路を切り替える~~ → **2 方の遮断弁**(下記「送風とバルブの部品選定」) | ファンは急に止められない。笛の流量がファンの能力に比べて小さいので、遮断してもファンから見た負荷はほぼ一定 |
| プランジャー | DC リニアアクチュエーター、**位置センサーなし** | これが作品の主張 |
| マイク | 笛の音を聞く | 唯一の位置フィードバック |

笛の流量はファンの能力に比べて小さく、ファンはほぼ締め切りで動くので、**バルブを開け閉めしてもファン側の圧力は
ほとんど動きません**(当初は流路切替の 3 方弁でこれを保証するつもりだったが、遮断で足りる)。閉じている間にたまった圧力で
開いた直後に少し上ずりますが、休符の長さで決まる**毎回同じように起きる再現性のある過渡**です。再現性があるということは、
実測して合わせ込めるということです(`scripts/calibrate.py` の仕事)。

吹き口の各部の呼び方: **ウィンドウェイ**(息の通り道)、**ブロック**(栓)、
**エッジ / ラビウム**(息が当たる刃)、**歌口**(開口部)。機構全体を **フィップル** と呼びます。

組み立て時の注意:

- ~~バイパス側の流路抵抗を笛側とそろえる~~(2 方の遮断弁にしたので不要)
- バルブは吹き口の近くに置く。バルブから吹き口までの容積が、発音の立ち上がりを遅くする。
  脈動をならすチャンバーを入れるなら、バルブより上流に置く
- ~~バイパスから出る風の音がマイクに入る~~(バイパスはなくなった。ファンの騒音は残る)

### 送風とバルブの部品選定(2026-09-18)

**ファン: BFB1012VH 型のシロッコファン**(97 × 94 × 33mm、12V 1.8A、5300rpm、静圧 2.814 inH₂O ≒ 700 Pa、4 線 PWM)。

- 見るべき数字は風量ではなく**静圧**。笛の流量(1 L/s 以下)はファンの最大風量(約 22 L/s)の 5% 程度で、
  ファンはほぼ締め切りで動く。そこで出る圧力がほぼ最大静圧になる
- 圧力は回転数の 2 乗にほぼ比例するので、PWM で絞って使う(50% で約 175 Pa、70% で約 340 Pa)。
  PWM 0% でも止まらないことが多いので、オン・オフは電源側の MOSFET で行う
- 回転数信号(タコ)を記録して、「圧力一定」の前提が守られているかを後から確かめる
- 弱点は騒音(64 dBA)。**ファンだけ回した録音のスペクトル**を最初に見て、箱・ホース・チャンバーの対策を決める
- 通販品は互換品が多く、静圧の表記は当てにしない。差圧センサー(〜1 kPa)で「PWM → 圧力」を実測する

落とした候補: 120mm・3600rpm の 2 線式(静圧の記載がなく、推定 350〜500 Pa。回転数は電源電圧で変えるしかない)、
50mm・3000rpm(静圧 65 Pa で足りない)。2 線式のブラシレスファンは中に駆動回路があるので、
**電源線を PWM で刻まない**(回転が揺れて、圧力と音程のゆらぎ・うなり音になる)。

**3 方弁をやめて 2 方の遮断弁にする。** ファンがほぼ締め切りで動くので、遮断しても圧力はわずかしか変わらない。
バイパスの風の音と、バイパスの流路抵抗をそろえる手間がなくなる。閉じている間にバルブの手前の圧力が少し上がるので、
開いた直後の過渡は実測して合わせ込む。

シミュレーター(`rig.py`、`torch_session.py`)もこれに合わせた。弁の手前のチャンバーは、閉じている間に締め切り圧力まで
たまり(時定数 `surge_tau`、公称 50ms)、開くと同じ時定数で笛から抜ける。そのぶん音程が `surge_cents`(公称 +10 セント、
機体差 ±8)× たまり具合だけ高くなる。**長い休符の後の音ほど上ずって入る**のが 3 方弁との違い。値はどれも推測で、
実測で合わせ込む。新しい機体の値は乱数の最後に引くので、同じ seed の他の値は変わらない。

この変更の前に学習した GRU(`runs/yamabiko_gru_first.npz`、学習し直していない)で比べ直した結果(200 台・5 曲、
鳴った音程のずれ): `gru` 27.6 / 19.3 / 19.3 / 19.4 / 19.1、`external_fit` 31.3 / 21.7 / 18.6 / 18.9 / 17.3、
`gru_reset` 27.6 / 25.4 / 26.2 / 27.3 / 26.3。下の「学習の結果」の表(3 方弁のシミュレーター)から
1〜2 セント以内の差で、結論は変わらない。曲とお手本の乱数の並びもずれるため、`open_loop` の数字はそれ以上に動く。

**バルブの条件: 最低作動圧力 0(直動式)で、口径が大きいこと。**

- 空圧機器の電磁弁はほぼパイロット式で、最低 0.02〜0.15 MPa が要る。ファンの 700 Pa では開かない
  (AirTAC 3V200、2V130 / 2V250、給水用の樹脂製 1/4 インチ弁はこれで不可)
- バルブとウィンドウェイは直列の絞りで、圧力は面積の 2 乗に反比例して分け合う。
  直動式の AirTAC 2V025(口径 2.5mm、Cv 0.25、有効断面積 約 4.3 mm²)だと、ウィンドウェイ(1 × 8mm と仮定)に届くのは
  700 Pa のうち約 300 Pa。2 個並列なら約 520 Pa

**本命は自作の回転円板弁(SCS0009 駆動)、控えが 2V025。** 吹き込み角度サーボをやめて余った SCS0009 を使う。

- 円板をサーボホーンに固定し、半径 20mm の位置に φ6 の穴。座面の φ6 の穴と重なると開、ずれると閉
- 開から閉まで円弧で約 8mm(穴径 + 重なり 2mm)、**約 23° ≒ 50ms**(600°/s)。2V025 の動作時間(50ms 以下)と同程度
- 力は 700 Pa × 28 mm² ≒ 0.02 N で、SCS0009 には負荷にならない
- 円板はファン側(上流)に置く。圧力で座面に押しつけられて閉じ、軸の貫通部から漏れてもファンの風が外に逃げるだけ
- 座面にシリコンシートか TPU のパッキン。閉じたときに笛がかすかに鳴らないかを確かめる
- 動いている間のモーター音がマイクに入る。電磁弁のカチッという音と同じく、影響を確かめる

## 先行作と、3D プリントの当て

### そのものの先行作: MIDI-Controlled Slide Whistle

<https://hackaday.io/project/174348-midi-controlled-slide-whistle>

ハード構成がやまびこ1号とほぼ同じです。

| 部位 | 先行作 | やまびこ1号 |
|---|---|---|
| 筒 | 1/2 インチ ID の PVC 管、400mm | 同方式。長さは音域から決め直す(下記) |
| ピストン | 8mm リニアシャフト + O リング(3D プリントの保持具) | 同じで良い |
| 送風 | シロッコファン + 3D プリントのフィップル | 同じ |
| 駆動 | NEMA17 ステッピング + ラック&ピニオン | **DC リニアアクチュエーター** |
| 位置 | **ステップ数の数え上げ(開ループ)。原点出しは手動、リミットスイッチは未実装** | **音程から推定** |
| 調律 | **手動。ステップ位置をソースに直接書く** | **自動(音で合わせる)** |

作者自身が「原点出しが手動」「O リングのはめあい調整に苦労した」と書いています。
**ここがやまびこ1号の差分そのもの**です。ステッピングは開ループで位置が出る代わりに、
原点出しが要り、脱調すると気づけず、個体ごとの調律を人が書く必要があります。
音を位置センサーに使えば、**原点出しも調律も要りません**(鳴らせば絶対位置が分かる)。

先行作があることは弱みではなく、**比較対象が実在する**という強みとして使えます。
STL / DXF / STEP が公開されています(STEP があるので改造できる)。ライセンスは要確認。

### フィップルの生成: flute-generator(MIT)

<https://github.com/axiomantic/flute-generator>

Python + OpenSCAD のパラメトリック生成。**MIT ライセンス**で、頭部(フィップル・ウィンドウェイ)を
胴体と分けて出力できます。ウィンドウェイの形(sac / arched / venturi / flat)も選べる。
本来は多管のドローン笛向けですが、頭部の生成だけ流用できます。

### 筒は 3D プリントしない

**内径は既製の管(PVC・アクリル・アルミ)を使うことを強く勧めます。**

プリントした内壁は粗く、真円度も出ません。管の内壁の粗さは音の安定性を落とし、
**音程のゆらぎ = 位置センサーのノイズ**として直接効きます。この作品では音程が唯一の
位置センサーなので、**筒の精度がそのままセンサーの精度**です。ここを妥協すると、
制御をいくら工夫しても取り返せません。

3D プリントするのは、フィップル頭部・ピストン保持具・バルブまわり・マウントに限ります。

### 筒の長さは音域から決める

閉管なので `L = c / 4f`。気温 25℃(音速 346.4 m/s)で、狙う音域 650〜1350 Hz に対して:

| 音 | 必要な管長 |
|---|---|
| 650 Hz(低い側) | 133mm |
| 1350 Hz(高い側) | 64mm |

つまり **管長 140mm 前後、ストローク 70mm 強**あれば足ります。先行作の 400mm は
216 Hz からの低い楽器で、狙いが違います。短いほうがアクチュエーターの移動距離が減り、
無音区間の開ループ誤差も小さくなるので有利です。

今のシミュレーターは `tube_len` 150mm / `stroke` 120mm([sim.py:47](../flute_rl/sim.py:47))で、
ストロークは必要より長めです。実機に合わせて詰める余地があります。

## 動作シナリオ

```
1. ファン オン、圧力が安定するまで待つ(バルブは閉)
2. 口笛を録音                          pitch.pitch_track
3. 音程軌跡をお手本に変換              targets.from_pitch_track
4. 演奏: バルブで音を出し入れしながら、プランジャーで音程をなぞる
5. ファン オフ
```

3 までは既存の実装([flute_rl/pitch.py](../flute_rl/pitch.py)、
[flute_rl/targets.py:190](../flute_rl/targets.py:190))でつながっています。

口笛は高い人だと 2kHz を超えますが、笛の想定音域は 650〜1350 Hz です
([flute_rl/targets.py:12](../flute_rl/targets.py:12))。
**音域外はオクターブ下げて真似る**仕様とします。やまびこは元々そういうものなので、
言い訳ではなく仕様として扱えます。

## 制御の構成

| 操作 | 型 | 誰が決めるか |
|---|---|---|
| プランジャー PWM | 連続 -1〜+1 | 制御器(学習の対象) |
| バルブ | 2 値(開 / 閉) | **お手本から決まった先回りで自動**(実装で決定、下記) |

実装では、バルブは学習の対象から外しました。音の入り切りはこの作品の主張ではなく、
バルブなら確実に止まるので、お手本の音の頭より「バルブ遅れ + 鳴り始め」ぶん早く開け、
音の終わりの「バルブ遅れ」ぶん前に閉じる固定の規則で十分だからです。

音が出ている間と出ていない間で、位置推定のやり方が切り替わります。

```
鳴っている:  フィードフォワード(位置信念で目標へ) + フィードバック(音程で位置信念を補正)
鳴っていない: フィードフォワードのみ(開ループ)。次の音の目標位置へ先回りする
```

無音区間は**次の音に向かって動く時間**として使い、鳴った瞬間に音で位置を取り戻します。
迷子になるのではなく、開ループになる時間に上限(休符の長さ、50〜120ms)がつくのが要点です。

### 開ループの誤差予算

`d(cents)/dx = 1200 / (ln2 · L)` なので:

| 管長 L | 位置 1mm あたり |
|---|---|
| 150mm(低音側) | 11.5 セント |
| 100mm(高音側) | 17.3 セント |

120ms の休符中に全速(150mm/s)で 18mm 動かすとして、
アクチュエーターの速さの誤差が残っていると:

| 速さの誤差 | 位置の誤差 | 発音時の音程の誤差 |
|---|---|---|
| ±20%(機体推定なし) | 3.6mm | 約 40 セント |
| ±6%(機体推定あり、相関 0.96) | 1.1mm | 約 13 セント |

つまり**機体推定は、無音区間の開ループ精度を買うためにある**。
テイクを重ねて上達するための道具ではなく、**1 テイク目のための道具**になります。
やまびこ(やり直しのない一発勝負)の筋書きと矛盾しません。

### 失うもの

正直に書いておきます。今までサーボの吹き込み角度は「速い微調整軸」でした
(600°/s、±50 セント程度)。フィップルにすると**音程の補正がすべて遅い直動軸に集まり**、
発音直後の誤差を素早く詰める手段がなくなります。ここは精度が落ちる方向の変更です。

送風圧を音程トリムに使う手はありますが、ファンが遅いこと、そして何より
**音程のずれが「位置由来」か「圧力由来」か切り分けられなくなり、
位置センサーとしての主張が濁る**ため、採りません。

## 記憶で機種に適応する(学習の中心)

### 考え方

エンコーダーがないので、ある瞬間の音程から分かるのは実効長 `L₀ + e − x` だけです。
位置・アクチュエーターの速さ・聞こえるまでの遅れ・管長のずれは、どれも
**「自分が出した PWM」と「聞こえた音程」の履歴を突き合わせないと分かりません**。
しかも位置の推定には速さと遅れが要り、速さと遅れの推定には位置の変化が要る。
**機種への適応と位置の推定は、同じ履歴からの同時推定**で、記憶がなければどちらもできません。

音程と位置の曲がった関係(`cents ∝ log L`)はどの笛でも同じ物理なので、事前学習で覚えます。
**記憶に残すべきなのは、機種ごとの数個の数字だけ**です。

### 方針(2026-09-17 決定)

**起動直後は下手で、数回吹くうちに合ってくる。機種の情報はモデルの再帰的な状態の中にだけ持つ。**

- 外部に校正値を持たない(`adapt.py` の当てはめも、`FluteParams` の保存もしない)
- 起動時のスイープのような特別な手順は入れない。普通に吹いているうちに慣れる
- 状態を初期化するのは**電源投入時だけ**。曲をまたいで持ち越す。笛を付け替えてもモデルには知らせず、自分で気づいて古い記憶を捨てる(実装で決定。付け替えデモの見せ場がここなので)

今の GRU は曲の頭で状態を初期化しているので、ここを変えます。
メタ強化学習の RL²(RNN の状態をエピソードをまたいで持ち越すと、適応の仕方自体を学ぶ)の形です。

### 学習の組み方

1. 機体を 1 台引く
2. **違う曲を K 曲続けて**吹かせる(K = 5 程度から)。状態は消さない
3. 一部の系列では、**途中で機体を入れ替える**(付け替えたら古い記憶を捨てることを学ばせる)
4. K 曲すべてのずれを報酬にする

報酬の重み: K 曲を同じ重みにすると 1 曲目から当てにいき、調べる動きを学びにくい。
**後の曲ほど重くする**と、序盤に多少外しても機種を掴むほうが得になる。
重みの付け方は実験で決める。

ES は勾配を時間方向に流さないので、K 曲分の長い系列でも学習が壊れにくい。
今の手法を続ける利点です。

### 必ず外すもの

**手作りの `x_hat`(`feedback.py`)と `adapt.py` を入力・構成から外す。** 残すと GRU が
そちらに仕事を任せ、記憶を使うことを学びません。これまでの GRU が
「耳を信じる度合いを一律 1.8 倍にするだけ」だった(`trust_analysis.py`)のは、これが原因と考えられます。

### 到達目標

外部に記憶を持つ `adapt.py` が、2 テイク目で **165 → 23 セント**(README 結果 2、甘いシム)。
**これをモデルの内部だけで再現する**。

|---|---|---|---|---|---|
| GRU(曲をまたいで記憶を持ち越す) | | | | | |
| GRU(曲ごとに記憶を消す) | | | | | |

1 行目が 2 行目から離れて 3 行目に近づけば、**記憶だけで機種に適応した**直接の証拠になる。
付け替え直後にいったん悪化し、また数曲で戻ることも同じ図で見る。

### なぜ合うようになったかを見る

演奏中の隠れ状態から、**真の位置・速さ・管長・遅れ**を線形回帰で読み出せるか調べる。
電源投入直後は読めず、数曲吹いた後に読めるようになれば、
演奏しながら機種を覚えたことの証拠になり、図としても見せやすい。

### デモ

1. 電源投入、口笛 → 1 回目のコピーは外れ気味
2. 2 回目、3 回目 → 合ってくる
3. **笛を付け替える** → いったん外れる → また数回で合ってくる

### 直すべき不整合: 裏返りは 12 度

閉管(片側を塞いだ円筒)は奇数次倍音しか出さないので、**裏返ると 3 倍音 = 12 度上(1902 セント)**
に飛びます。オクターブ(1200 セント)ではありません。クラリネットと同じです。

今の実装は閉管モデル(`f = c / 4L`)なのに裏返りを +1200 セントにしていて、一貫していません。

| 場所 | 現状 | 正しい値 |
|---|---|---|
| [sim.py:217](../flute_rl/sim.py:217) | `cents += 1200.0` | `1902.0` |
| [torch_sim.py:85](../flute_rl/torch_sim.py:85) | `+ 1200.0 * overblown` | `1902.0` |
| [sim.py:292](../flute_rl/sim.py:292) | `±1200`(音程推定器のオクターブ誤り) | **そのまま**(別物) |

物理層の書き直しに合わせて直します。制御への影響は 2 つ: 誤差が 1902 セントとして現れるので
`feedback.py` の `max_err=300` で確実に弾ける(オクターブ誤りより検出しやすい)一方、
音楽的には 1200 より遠くに飛ぶので、聞こえ方の被害は大きくなります。
| 駆動 | `angle_range_deg`, `servo_rate_dps`, `servo_tau`, `servo_step_deg` | リニアアクチュエーター一式(`v_max_in/out`, `deadband`, `tau_v`, `cmd_delay`, `backlash` と harsh の `stiction`, `pwm_curve`, `load_slope`, `speed_drift`, `motion_noise`, `delay_jitter`) | — |
| 送風・バルブ | — | `onset_s`(意味が変わる: 風が来てから音が立つまで) | バルブ動作遅れ(開閉で非対称)、吹き口までの容積による立ち上がり、消音の速さ、発音直後の音程の過渡 |
| 聞き取り | — | `obs_delay`, `octave_err`, `pitch_noise`, `dropout` | — |

`onset_s` は消えずに**意味だけ変わります**(「鳴り始めの窓に入ってから」→「風が届いてから」)。

観測からは `angle_readback` と `angle_comp` が消えます。
`angle_comp` は「唯一のキャリブレーション」でしたが、フィップルでは不要になります。

`harsh` の枠組み自体は残します。消える複雑さ(エッジトーン)の代わりに、
**発音の過渡**が制御側の知らない効果として入ります。手で書きにくく、実測で合わせられる、
という意味で良い交換だと考えています。

## 評価指標

今の「テイク全体の音程のずれの平均」だと、この作品の構造が見えません。新設します。

| 指標 | 内容 | 何を見るか |
|---|---|---|
| 発音直後の誤差(純粋) | 音が立った**最初の 1 ステップ**のずれ | フィードフォワード単独の精度。どの個体でもフィードバックが届いていない |
| 発音直後の誤差(実用) | 音が立ってから 5 ステップの平均のずれ | 開ループ(無音区間)の精度 = 機体推定の質 |
| 収束時間と収束率 | 発音から、ずれが 20 セント以内に入るまで。**収束率を必ず併記**し、収束時間は収束したものだけで出す | 観測器の質 = 学習の効きどころ |
| 定常時の誤差 | 音を伸ばしている間のずれ | フィードバックが効いた後の地力 |
| 音が出ている割合 | 鳴るべき区間で鳴っていた割合 | 黙って罰を避ける癖が出ていないか |
| オクターブ誤りによる暴れ | 誤った音程を位置に反映してしまった回数 | 観測器の頑丈さ |

閾値 20 セントの根拠: 音程推定ノイズ(3 セント)より十分大きく、位置に直すと約 2mm で
機械的に意味のある量。収束前に音が終わるケースは打ち切りデータなので、単純な中央値は
嘘をつきます。必ず収束率とセットで読みます。

既存の `gap_leak`(音符の間の無音で鳴ってしまった割合)は役目が変わります。今までは
吹き込み角度を窓の外に振る難しい動作でしたが、バルブなら確実に止まる。制御の巧さではなく
**バルブのタイミングの指標**になるので、残しますが主要指標からは外します。

「音が出ている割合」はバルブ式でも外せません。バルブを閉じたままなら黙れるので、
**以前より簡単に報酬ハックできます**。

### 制御器

どれも「次の音の位置(公称の管のモデルで換算)に向けて、位置の見込みで PWM を出す」形で、
**位置の見込みをどこから得るか**だけが違います。

| 名前 | 位置の見込み | 機体の記憶 |
|---|---|---|
| `open_loop` | 出した PWM を公称のモデルで積算 | なし |
| `encoder` | 真の位置(センサーあり)。管のモデルは公称のまま | なし |
| `oracle` | 真の位置 + その機体の真の管のモデル(上限) | — |
| `observer` | 積算 + 遅れて聞こえた音程で補正(手作り) | **曲ごとに忘れる** |
| `external_fit` | observer + 聞こえた音程から速さ(押し・引き別)と管のずれを最小二乗で当てはめ、次の曲で使う | **モデルの外**に 3 つの数として持つ |
| `gru` / `gru_reset` | 積算 + GRU の出力 (a, b, c) で `(1+a)·押した量 − (1+b)·引いた量 + c` | **GRU の隠れ状態の中だけ**(`gru_reset` は曲ごとに消す対照) |

GRU について決めたこと:

- 積算(押した量・引いた量)は公称のモデルで、原点出しのたびに消える。機体の情報を持たない
- 出力を「位置の見込みの補正 (a, b, c)」にした。PWM を直接出させるより ES で見つけやすい形にするための構造で、
  機体の情報は毎ステップ隠れ状態から出し直すので、外に記憶は残らない
- 入力には、聞こえた音程と「公称の遅れ(3 ステップ)ぶん前の見込み」の差を入れる。本当の遅れ(1〜5 ステップ)は機体ごとに違うので、そのずれは記憶で覚える必要がある
- 裏返った音(12 度上)は 1902 セント引いて基音として使う(楽器の物理なので、手作りの観測器と同じ規則で前処理)
- 初期値は読み出しがゼロで、`open_loop` とまったく同じ演奏になる(テストで確認)

### 実装中に分かったこと

- **手作り観測器の「大きくずれた音は無視する」ゲートは罠だった。** 最初は 300 セント以上のずれをオクターブ誤りとして捨てていたが、
  機体差で 300 セント以上ずれた機体では一度も補正できず、戻れなくなった。裏返りも同じ理由で抜け出せなかった。
  「前のフレームから音程が跳んだら捨てる」(1 フレームだけのオクターブ誤りを除く)と「裏返りは 1902 セント引く」に変えて解消
- 裏返りの境界は、最も高い音(1350 Hz、管の実効長 約 63mm)の近くに置くと、行き過ぎた機体が裏返ったまま戻らない。
  境界を 50±4mm にして余裕を持たせた
- 「暴れ」の数え方: レガートで目標の音が切り替わった直後の追従遅れまで数えていて、上限の `oracle` でも 100 発音あたり 8〜16 回出ていた。
  直近 150ms に目標が半音以上動いた区間は、定常誤差と暴れから外した(`oracle` は 0 回に)

## 学習の結果(2026-09-18、甘いシミュレーター、`harsh=0`)

### GPU で学習する

学習部分だけ PyTorch に移しました(`flute_rl/yamabiko/torch_session.py`、`--device cuda`)。
機体・原点出し・バルブ・GRU・報酬を候補 × 機体ぶんまとめて進め、**1 ステップ全体を CUDA graph で再生する**ので、
1 ステップの起動は台数によらず 1 回です。numpy 版は基準として残し、機体の乱数を切った float64 では
報酬が一致します(`tests/test_yamabiko_torch.py`)。乱数を入れると系列は違いますが、統計は一致します。

| | 1 世代 |
|---|---|
| numpy・16 プロセス、64 候補 × 8 台 | 1.3 秒 |
| GPU(RTX 5060 Ti)、256 候補 × 64 台 | 1.9 秒 |

計算量 32 倍がほぼ同じ時間で回るので、**候補あたりの機体数を 8 から 64 に増やしました**。

### つまずき: 記憶が数ステップしか持たない

最初の学習では、`gru` と `gru_reset` の結果が小数点以下まで同じでした。**記憶がまったく使われていません**でした。
原因は GRU の初期値で、更新ゲートの偏りが 1 前後だと記憶の半減期が 2 ステップ程度しかなく、
1 曲(約 1,000 ステップ)の間に前の曲の情報が消えます。ES のノイズ幅ではこの偏りはほとんど動きません。

各ユニットの時定数を 2 〜 3,000 ステップに散らす初期化(chrono 初期化、`--memory-steps 3000`)に変えたら、
25 世代で `gru_reset` との差が出ました。**ここが学習の成否を分けた一点**です。

### 最初の音を重く見る

曲の最初の音は、原点出しで推測航法が消えてから一度も音を聞いていない状態で当てにいく音で、
**記憶が効くかどうかが最もはっきり出ます**。指標に `first1`(曲の最初の音の、発音した最初のステップのずれ)を足し、
報酬でもこの音を 8 倍に重くしました(`--first-weight 8`)。

```bash
python scripts/yamabiko_train.py --device cuda --gens 400 --pop 256 --rigs 64 --songs 5     --memory-steps 3000 --first-weight 8 --out runs/yamabiko_gru_first.npz
```

  記憶がなければ当てようがない。**「起動直後は下手」はここに最もはっきり出るので、デモはこの音を聞かせる**

| **`gru`** | 19.3 | 32.4 | **20.8** | **18.6** |

GRU は 1 曲で戻り、`external_fit` は引きずったままです(忘れ方が 1 曲 0.7 倍の固定のため)。

### 隠れ状態から機体の値を読み出す(R²、学習に使っていない機体)

| | 電源投入直後 | 1 曲後 | 5 曲後 |
|---|---|---|---|
| 押す向きの速さ | 0.00 | 0.60 | 0.63 |
| 管長のずれ | 0.00 | 0.15 | 0.13 |

電源投入直後は読めず、1 曲吹くと読めるようになります。ただし、はっきり覚えているのは押す向きの速さだけで、
引く向きの速さ・遅れ・デッドバンドは読めません。原点出しが引き切るだけで突き当てて止まる(動いていない)ため、
機体の速さを知る手がかりが演奏中の音しかなく、原点から演奏位置へ向かう最初の大きな動きが必ず押す向きだからだと
考えていますが、確かめていません。
